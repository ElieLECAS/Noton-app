## Phase 1 — Ingestion sur OCR 4 (~2-3 semaines)

Objectif : remplacer la transcription vision page-par-page (non déterministe, sans garantie)
par une extraction structurée déterministe, et redéfinir le rôle exact de chaque niveau
de chunk.

### 1.1 Architecture cible

> **Maîtrise du coût OCR — routage « couche-texte-d'abord ».** Mesure sur le corpus local
> (39 docs, 2 316 pages) : **91 % des pages ont déjà une couche texte exploitable**
> (25 docs nativement textuels, 12 mixtes, 2 scannés). L'OCR payant ne doit donc traiter
> que les ~9 % de pages scannées/visuelles. Le coût OCR 4 devient un coût UNIQUE
> (jamais re-payé grâce aux IDs stables) et marginal : ~180 $ batch pour 1 M de pages au
> total (vs 2 000 $ en OCR-isant tout). Au-delà de quelques centaines de k pages,
> auto-héberger OCR 4 (conteneur unique) sur le VPS annule le coût par page.
> NB : ce routage natif→OCR existait dans `pdf_extraction_service.py` (docstring) puis a
> été perdu ; on le reconstruit.

```
PDF → ROUTAGE PAR PAGE (déterministe, gratuit — pymupdf)
      couche texte ≥ seuil ?
        page native SANS tableau      → pymupdf get_text            (gratuit)
        page native AVEC tableau       → pymupdf find_tables          (gratuit)
                                         └─ si extraction douteuse → OCR 4 (sélectif)
        page scannée / image-only      → Mistral OCR 4               (payant, ~9%)
      → blocs typés uniformes : {type: title|text|table|equation|…, bbox, page, markdown,
        confiance} — MÊME schéma quel que soit l'extracteur, l'aval ne voit pas la différence
  → RECONSTRUCTION DE SECTIONS (déterministe)
      titres → arbre de sections ; liaison inter-pages GÉOMÉTRIQUE :
      dernier bloc texte de page N sans terminaison + premier bloc de page N+1
      compatible (même type, même section) → fusion.
      Cas ambigus (~5%) → arbitrage LLM mistral-small (décision binaire "même phrase ?")
  → CHUNKING STRUCTUREL (déterministe, zéro LLM)
      section courte → 1 chunk ; section longue → split par tokens (350-480) SUR
      frontières de paragraphes ; tableau → 1 chunk/ligne {headers+row} + 1 chunk résumé ;
      liste → liste entière avec son titre parent
  → INVARIANT DE COUVERTURE : chaque bloc OCR ∈ exactement 1 chunk (assert, log des gaps)
  → GATE DE FIDÉLITÉ NUMÉRIQUE (sur toute sortie LLM aval)
  → IDs STABLES : node_id = sha256(document_id, page, contenu_normalisé)[:16]
      → réindexation incrémentale : embeddings/ColPali recalculés SEULEMENT si hash changé
  → KAG + ENRICHISSEMENT (voir 1.3) → EMBEDDINGS → ColPali (inchangé, streaming par fenêtres)
```

La vision LLM (mistral-small/Pixtral) ne sert plus qu'aux pages à faible densité de texte
OCR (schémas CAO, éclatés) pour produire un chunk descriptif complémentaire — jamais comme
source primaire de texte.

### 1.2 Niveaux de chunks — rôles redéfinis

| Niveau | Contenu | Produit par | Embedding | BM25 | Packé en génération (CAG) |
|---|---|---|---|---|---|
| L0 `page_anchor` | ancre de page (support ColPali) | déterministe | non | non | non |
| L1 `structural` | verbatim structuré (sections, lignes de tableaux) | déterministe (OCR 4) | oui, avec préfixe contextuel | oui, MÊME préfixe (fin de l'asymétrie) | **oui — seul niveau packé** |
| L2 `contextual` | synthèses/fiches IA | LLM (voir 1.3) | oui | oui | **non** (voir 1.4) |
| L3 `visual_desc` | description de page visuelle | LLM vision | oui | oui | oui si page packée |

### 1.3 Chunks générés par IA — réponse à « toujours 3 pages avec overlap 1 ? »

**Non.** La fenêtre fixe 3 pages / overlap 1 (stride 2) est un pis-aller d'aujourd'hui :
elle existe parce que le pipeline actuel ne connaît pas la structure logique du document.
Elle a deux défauts prouvés par l'audit : la page partagée est enrichie deux fois sans
dédup (doublons systématiques), et une section de 5 pages est coupée arbitrairement en
3 morceaux qui se recouvrent mal.

**Cible : l'unité d'enrichissement devient la SECTION LOGIQUE**, reconstruite en 1.1
(une section = 0,5 à N pages, les frontières de pages n'existent plus à ce stade) :

- 1 appel LLM (mistral-small) par section, avec en entrée : la section complète (verbatim),
  le chemin de titres (document › chapitre › section), les métadonnées doc (gamme, matériau).
- Sortie : 0 à 2 chunks contextuels par section, selon le playbook de sa catégorie —
  `synthesis` (résumé self-contained), `procedural_step` / `diagnostic_unit`
  (fiches structurées pour les guided trees). Une section déjà courte et autoporteuse
  ne produit RIEN (économie ~40 % d'appels vs fenêtres fixes).
- Sections très longues (> ~6 000 tokens) : fenêtrage PAR TOKENS avec overlap 0,
  frontières sur paragraphes — jamais par pages.
- Dédup par hash de contenu ; `source_pages` + `source_node_ids` conservés en métadonnées
  pour la traçabilité et les citations.
- **Interdiction de réécrire les valeurs** : le gate de fidélité numérique rejette tout
  chunk L2 contenant un nombre/référence absent des chunks L1 sources. Le L2 cite
  (« voir tableau p.12 »), il ne recopie pas les cotes.
- Le KAG (extraction entités/relations) suit la même bascule : par section, plus par
  fenêtre de pages. La notion de `KAG_BATCH_SIZE`/`OVERLAP` disparaît.

Transition : si un réindexage complet n'est pas possible immédiatement, correctif minimal
sur l'existant = garder 3 pages mais **overlap 0** + dédup par `(theme, source_page)` —
ça supprime les doublons sans rien casser.

### 1.4 Usage des chunks IA dans la génération — réponse à la 2ᵉ question

**État actuel (vérifié dans le code) : oui, ils sont dans le prompt de génération, et
c'est un défaut.** Les L2 sont `is_leaf=True` (`contextual_enrichment_service.py:693,712`)
et le packer CAG charge tous les `is_leaf=True` du document sélectionné
(`context_packer_service.py:100-103`). Résultat : le prompt contient le verbatim L1
PLUS ses paraphrases L2 (×2 sur les pages chevauchées) — le même fait y figure 2 à 3 fois,
soit ~30-50 % du budget CAG gaspillé en redondance, avec le risque qu'une paraphrase
contredise le verbatim.

**Cible : les L2 servent au RETRIEVAL, pas au PACKING.**
- Retrieval : les L2 restent embarqués (embedding + BM25). C'est là qu'ils paient — une
  synthèse self-contained matche des questions que le verbatim fragmenté rate. Un hit L2
  vote pour son document/sa page dans la fusion, comme n'importe quel hit.
- Génération : le packer CAG ne charge QUE les L1 (+L3 si page visuelle packée) —
  filtre `content_type != 'contextual_enrichment'` dans `_load_leaf_records`. Le document
  verbatim complet est déjà dans le contexte ; la paraphrase n'apporte aucune information
  et le modèle de génération n'a pas besoin qu'on lui prémâche.
- Exception : les fiches structurées (`procedural_step`/`diagnostic_unit`) restent la
  source des guided trees via `metadata_json["structured"]` — usage hors prompt, inchangé.

Ce seul filtre est applicable dès la phase 0 si besoin (1 ligne + invalidation du cache
fulltext) : gain immédiat de budget tokens sans toucher à l'indexation.
