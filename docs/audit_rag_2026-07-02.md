# Audit critique du système RAG Noton — 2026-07-02

> Audit multi-agents (ingestion, KAG/catégories, retrieval, génération/conversation, frontend).
> Complémentaire à `constat_etat.md` (2026-04-15) qui couvrait sécurité/fiabilité — ici l'axe est la **qualité RAG, la latence et la conversation**.
> Les latences et coûts sont des estimations à valider par instrumentation.

---

## 1. Diagnostic des trois plaintes utilisateur

### 1.1 « Le temps de réponse est long »

**Cause racine : 4 à 6 appels LLM séquentiels AVANT le retrieval**, dans le graphe de query understanding (`app/services/lightweight_query_understanding.py`) :

| Étape | Flag | Latence estimée |
|---|---|---|
| Route decision (direct vs rag) | toujours | ~0.8–1.5 s |
| Extract signals | toujours (si rag) | ~1.0–1.8 s |
| Assess vagueness | `QUERY_VAGUENESS_CHECK_ENABLED=true` | ~0.8–1.2 s |
| **Condense question (nouveau)** | `QUERY_CONDENSE_ENABLED=true` | ~1.0–1.5 s |
| Plan multi-query | `QUERY_MULTI_GROUP_ENABLED=false` (off) | — |
| Generate queries (colpali/semantic/lexical) | toujours | ~1.0–1.5 s |

→ **~5–7 s bloquants avant le premier accès aux index**, tous en chaîne sur `mistral-small-latest`.

Ensuite s'ajoutent, toujours séquentiellement :
- Retrieval quadruple exécuté **en séquence** (ColPali CPU ~400 ms, pgvector, BM25, KAG) dans `space_search_service.py:746-753` alors qu'il est parallélisable.
- Rerank cross-encoder CPU (~50–100 ms), vision rerank LLM (jusqu'à 4 pages), rendu PNG des pages (2–5 s si modèle vision), extraction d'illustration (2–5 s, **bloque l'événement `done`**, `chat.py:1403-1430`).

**Total avant premier token visible : ~9–18 s** dans le pire cas. Le frontend n'affiche qu'un spinner générique pendant tout ce temps → latence perçue maximale.

### 1.2 « La conversation se perd, surtout au changement de sujet »

Trois mécanismes se combinent :

1. **Le condense traîne l'ancien sujet.** `CONDENSE_QUESTION_SYSTEM_PROMPT` (`lightweight_query_understanding.py:242-255`) demande de « résoudre les références implicites en réintégrant le contexte » mais **ne donne aucune règle pour détecter une rupture de sujet**. « Oublie le profil 76, parle-moi du DTU 36.5 » risque d'être reformulé en « À quoi sert le DTU 36.5 pour la pose du profil 76 ». Les tests (`tests/test_query_condense.py`) ne couvrent que le suivi immédiat, aucun test de changement de sujet.
2. **Les signaux du tour N-1 polluent le tour N.** `Conversation.query_context` persiste signals/source/matériau et `_node_merge_context` les fusionne sans jamais les réinitialiser. Les soft boosts (`apply_soft_boosts_to_passages`, `refine_with_source_authority`, `chat.py:955-971`) rehaussent donc des documents de l'ancien sujet (ex. alu boosté alors qu'on parle désormais de PVC).
3. **Aucun état de « sujet courant »** ni détection de dérive : l'historique est concaténé linéairement (10 messages / 8 000 chars) sans marqueur de rupture.

### 1.3 « Est-ce que je donne assez de contexte à la génération ? »

Le budget contexte est **modeste mais ce n'est pas le vrai problème** :
- ~18 000 chars de passages max (~5 000 tokens), passages tronqués individuellement, dynamic K borné à `MAX_DYNAMIC_K=12` avec **`MIN_DYNAMIC_K=0`** → un rerank peu confiant peut envoyer **0–2 passages** au LLM (risque d'hallucination ou de refus).
- La fenêtre Mistral (32k+) est très loin d'être remplie (~9k tokens utilisés au total). Il y a de la marge pour doubler le contexte sans risque.
- Le vrai goulot est **la qualité du ranking** (reranker anglais, boosts pollués, condense faussé) : donner plus de chunks mal classés n'améliorera rien ; corriger le ranking puis augmenter `MAX_DYNAMIC_K`/le budget chars, oui.
- `MAX_COMPLETION_TOKENS=1024` / `SPACE_CHAT_MAX_TOKENS≈1200` : les réponses procédurales longues peuvent être coupées en plein milieu.

## 2. Constats majeurs par sous-système

### 2.1 Retrieval & fusion (le cœur)

- 🔴 **Reranker cross-encoder `ms-marco-MiniLM-L-6-v2` = modèle ANGLAIS** (`reranker_service.py:104`) appliqué à un corpus 100 % français, technique menuiserie. Les seuils calibrés dessus (`RAG_MIN_PERTINENCE=0.75`, offset sigmoïde +1.5, guardrails « bégaiement ») sont donc invalides. Remplacer par un cross-encoder multilingue (`mmarco-mMiniLMv2-L12`) ou un reranker API (Cohere rerank-multilingual, Jina).
- 🔴 **Retrievers exécutés en séquence** (`space_search_service.py:746-753`) : ColPali (CPU) + pgvector + BM25 + KAG parallélisables → ~-30 % de latence retrieval.
- 🟡 **Cascade de filtres pouvant vider le contexte** : seuils ColPali (min 0.30, post-fusion 0.25) + `RAG_MIN_PERTINENCE=0.75` + `MIN_DYNAMIC_K=0` + guardrail low-confidence. Plusieurs chemins mènent à un contexte quasi vide sans que l'utilisateur le sache.
- 🟡 **Category boost multiplicatif sur le score RRF avant rerank** (`retrieval_boost_service.py:106-164`) : jusqu'à ×1.9 avec 3 catégories symptôme. Amplifie les erreurs de classification LLM (précision estimée ~70–85 %) et peut inverser des rangs légitimes.
- 🟡 ColPali query encoding sur CPU dans le chemin critique (~100–400 ms), index LanceDB IVF_SQ créé « lazy » (scan linéaire silencieux tant que < ~1000 vecteurs).

### 2.2 Génération & grounding

- ✅ Prompt système de génération solide (grounding strict, interdiction d'assembler des cotes, « la notice ne précise pas »).
- 🔴 Mais **aucune vérification post-génération** : `chat_critique_service.py` existe et n'est jamais appelé en streaming (`FAQ_POST_DRAFT_ENABLED=false`).
- 🟡 Les citations : le prompt interdit les marqueurs `[Doc, page X]` mais le code cherche ces patterns par regex pour lier les sources (`chat.py:1339-1390`) → le fallback « sources par score » s'applique presque toujours ; l'ancrage citation↔passage est illusoire.
- 🟡 Sources envoyées au front en un bloc après la fin du stream — l'utilisateur lit la réponse avant de savoir d'où elle vient.

### 2.3 Ingestion / chunking / embeddings

- ✅ Architecture 2 niveaux saine (page_anchor L0 + semantic_leaf L1 vision ~256–480 tokens, métadonnées riches, merge cross-page).
- 🔴 **Enrichissement contextuel L2 = risque d'hallucination indexée** : le prompt demande d'« EXPLICITER » avec expertise métier, sans fact-check contre le texte source, et ces chunks générés sont embeddés au même titre que le texte réel, sans marquage `llm_generated`.
- 🔴 **Export/import très incomplet** (`routers/library.py:1410-1850`) : le ZIP exporte fichier + chunks + embeddings + patches ColPali mais **PAS le graphe KAG, PAS les catégories, PAS les classifications document** (product_types, materials, gammes) → un import sur une autre instance perd la moitié de l'intelligence.
- 🔴 **`delete_document` ne nettoie pas le KAG** (`document_service_new.py:1111-1148`) : entités/relations orphelines s'accumulent, graphe corrompu au fil des suppressions/réimports.
- 🟡 Pas de limite de taille/MIME à l'upload ; métadonnées appliquées seulement au 1er fichier en upload multiple ; retry Celery unique (doc bloqué `pending` sur erreur transiente) ; pas de transaction entre PostgreSQL et LanceDB.
- 🟡 Chunks vides silencieusement non embeddés ; pas de seuil minimal (micro-chunks footers) ; DPI fixes (300 extraction / 150 ColPali) non adaptés au type de page.

### 2.4 KAG & catégories

- Architecture propre (contraintes d'unicité, aliases, hop limit 1) mais **ROI douteux en l'état** : ~10–40 appels LLM/document à l'ingestion pour +2–5 pages différentes par requête, avec du bruit.
- 🔴 **Résolution d'entités faible** : « 6104 », « Profil 6104 », « 76180 AA » créent des entités distinctes ; matching requête par trigram seuil 0.35 permissif ; pas de déduplication sémantique ni lexique métier (la vraie solution pour la menuiserie : un référentiel produits → codes/alias).
- 🟡 Hop 1 large (100 relations voisines, facteur 0.65) → co-occurrence ≠ pertinence.
- 🟡 Catégories : taxonomie 4 axes bien conçue, mais prédiction LLM imparfaite + `CATEGORY_MIN_CONFIDENCE=0.55` bas + boost ×2 sur symptom = amplification d'erreurs. `CategoryCandidate` s'accumule en pending sans workflow de promotion.

### 2.5 Frontend

- 🔴 **Aucune transparence pipeline** : spinner générique pendant 9–18 s ; le backend a 5 phases distinctes mais n'émet aucun événement d'étape SSE (« Recherche… », « Analyse de N pages… », « Génération… »).
- 🔴 **Pas de feedback 👍/👎 dans le chat** (la page /feedbacks existe mais est déconnectée du fil).
- 🟡 Monolithe : `project_detail.html` ~2 858 lignes, logique de streaming dupliquée entre `index.html` et `project_detail.html` (~850 lignes ×2). Pas de retry réseau, pas de timeout client, accessibilité faible.
- 🟡 Sources : badges cliquables mais pas d'aperçu de la page PDF d'origine (PDF.js pourtant déjà chargé), numérotation fragile.

## 3. Plan d'action priorisé

### P0 — Corriger la conversation et la latence (le ressenti utilisateur)

1. **Détection de changement de sujet + reset** :
   - Enrichir le prompt du condense : « Si le dernier message introduit un sujet sans lien ou demande d'oublier le précédent, retourne-le tel quel sans réintégrer l'historique » + champ de sortie `topic_shift: bool`.
   - Sur `topic_shift`, purger `Conversation.query_context.signals` avant les soft boosts.
   - Ajouter les tests manquants (« oublie X, parle de Y », suivi après 5 tours).
2. **Réduire les appels LLM pré-retrieval** : fusionner route + signals + condense en **un seul appel JSON** (un schéma de sortie combiné) ; garder vagueness dans le même appel. Objectif : 1 appel (~1.5 s) au lieu de 4–5 (~6 s).
3. **Paralléliser les 4 retrievers** (`asyncio.gather`) et sortir l'extraction d'illustration/le rendu d'images du chemin bloquant (émettre `done`, pousser l'illustration en événement SSE tardif).
4. **`MIN_DYNAMIC_K=3`** pour ne jamais générer sur contexte vide, et passer explicitement `SPACE_CHAT_MAX_TOKENS` (≥2000) à l'API pour les réponses procédurales.
5. **Événements d'étape SSE + affichage frontend** : latence perçue divisée même sans optimisation réelle.

### P1 — Qualité du ranking (le grounding réel)

6. Remplacer le reranker par un modèle **multilingue** et recalibrer tous les seuils dépendants (`RAG_MIN_PERTINENCE`, offset sigmoïde, guardrails) sur un jeu d'éval FR menuiserie (50–100 requêtes annotées — `retriever_evaluator.py` existe déjà, s'en servir).
7. Réduire `RETRIEVAL_CATEGORY_BOOST` ou l'appliquer post-rerank ; monter `CATEGORY_MIN_CONFIDENCE` vers 0.70.
8. Une fois le ranking fiabilisé : augmenter le budget contexte (`MAX_DYNAMIC_K` → 16–20, budget chars → 30k) — la fenêtre Mistral le permet largement.
9. Activer une critique post-génération légère en streaming (vérif entailment réponse↔passages) ou au minimum réconcilier le mécanisme de citations (soit le prompt autorise `[n]`, soit supprimer les regex mortes).

### P2 — Intégrité des données

10. `delete_document` → cleanup KAG + catégories ; vérifier les cascades FK.
11. Export/import complet : graphe KAG, ChunkCategoryRelation, classifications document, dans le ZIP.
12. Limite taille/MIME upload ; métadonnées appliquées à tous les fichiers d'un upload multiple ; retry Celery ≥3 avec backoff.
13. Marquer les chunks L2 `llm_generated` + fact-check simple (recouvrement lexical avec le source) avant indexation.

### P3 — Dette & coûts

14. A/B tester KAG (on/off) avec l'évaluateur avant d'investir plus ; sinon construire un **lexique produit** (référence → alias) qui rendra service à la fois au KAG, au condense et à la fiche technique.
15. Factoriser le JS de chat (`chat-manager.js` partagé), feedback 👍/👎 inline, aperçu PDF des sources.
16. Supprimer `document_service.py` (déprécié) et les flags de config morts.
